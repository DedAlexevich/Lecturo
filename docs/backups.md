# Бэкапы базы на локальном стенде

Контейнер `db-backup` в `docker-compose.yml` делает `pg_dump` базы `lecturo` раз в сутки и кладёт дампы в `data/backups` (`${DATA_DIR}/backups`) на хосте, то есть вне контейнеров и вне `data/postgres`. Хранятся последние 7 копий, старые удаляются. Бэкапы на сервере описаны в [deploy.md](deploy.md#бэкапы-базы). Ручной дамп, восстановление и проверка используют те же скрипты `infra/backup`, что и сервер (`common.sh`), а плановый дамп внутри контейнера делает `infra/backup/schedule.sh` с теми же именами файлов и правилом ротации.

## Автоматические бэкапы

Контейнер стартует вместе с проектом (`docker compose up`), первый дамп делает сразу, следующий через `BACKUP_INTERVAL_HOURS` часов (по умолчанию 24). Расписание не сбивается при перезапусках: если свежий дамп уже лежит в папке, контейнер ждёт оставшееся время. Файл сначала пишется во временный и проверяется через `pg_restore --list`, а в `lecturo-<дата>-<время>.dump` переименовывается только после проверки. Время в имени файла UTC. Сообщения контейнера: `docker compose logs db-backup`.

Папка `data/backups` доступна на запись всем, а дампы контейнера читаются всеми: так дампы, сделанные вручную с хоста, лежат рядом с дампами контейнера, а восстановление не требует `sudo`. Для локального стенда с тестовыми данными это приемлемо; на сервере папка принадлежит `deploy` и группе `lecturo-backups` с правами `2770` (см. [deploy.md](deploy.md)). На сервере контейнер не запускается (профиль `local` в `infra/compose.prod.yml`), там работает таймер systemd.

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `BACKUP_KEEP` | Сколько копий хранить | `7` |
| `BACKUP_INTERVAL_HOURS` | Период между дампами, часы | `24` |
| `BACKUP_DIR` | Другая папка для бэкапов | `${DATA_DIR}/backups` |

## Ручной дамп

```
scripts/backup-db.sh
```

Скрипт делает дамп немедленно, проверяет его восстановлением во временный контейнер (`check.sh`), кладёт в ту же папку и учитывает `BACKUP_KEEP`. Локально шифрование и выгрузка выключены: `BACKUP_AGE_RECIPIENT` и `BACKUP_S3_*` в `.env` пустые, о чём скрипт пишет предупреждение. Проект должен быть запущен: дамп снимается через `docker compose exec db`.

## Восстановление

```
scripts/restore-db.sh data/backups/lecturo-<дата>-<время>.dump
```

Скрипт просит ввести `yes`, сохраняет текущую базу в `pre-restore-<дата>-<время>.dump` (хранятся три последних), останавливает `api`, `worker` и `bot`, пересоздаёт базу, загружает дамп и поднимает сервисы обратно. Если дамп старее кода, недостающие миграции применит сервис `migrate` перед стартом `api`. Если восстановление упало, сервисы остаются остановленными, а скрипт печатает путь к сохранённой прежней базе.

Нужно, чтобы контейнер `db` работал. Если база повреждена и не стартует, остановите проект, переложите `data/postgres` в сторону (удаление требует `sudo`, см. [data.md](data.md)), поднимите проект с пустой папкой и восстановите дамп этой командой.

## Проверка восстановления

```
infra/backup/check.sh data/backups/lecturo-<дата>-<время>.dump
```

Скрипт поднимает временный контейнер Postgres без сети, восстанавливает в него дамп и печатает ревизию миграций, число таблиц и пользователей. Рабочая база не затрагивается, контейнер удаляется в любом случае. Без аргумента проверяется самый свежий дамп из `BACKUP_DIR`: `check.sh` не знает про `DATA_DIR`, поэтому для локального стенда передавайте файл явно или задайте `BACKUP_DIR=./data/backups`.

Бэкапы лежат на том же диске, что и база. От удалённых строк и неудачной миграции они спасут, от потери диска нет: время от времени копируйте `data/backups` в другое место.

## Из админ-панели

Раздел «Бэкапы» в `/admin` работает с той же папкой `BACKUP_DIR`: контейнер `api` видит её как `/backups` и использует `pg_dump` и `pg_restore` версии 16 из образа. Docker-сокет контейнеру не нужен, поэтому дамп по кнопке делается напрямую через `pg_dump -Fc`, а не скриптами из `infra/backup`.

- Список показывает дамп, дату, размер и результат `pg_restore --list`. Зашифрованные `.tar.age` можно скачать, но не восстановить: ключа на сервере нет.
- «Создать дамп» кладёт `manual-<дата>-<время>.dump`. Загруженный файл сохраняется как `uploaded-<дата>-<время>.dump` и сам не применяется. Ротация `BACKUP_KEEP` трогает только `lecturo-*.dump`, ручные дампы удаляются кнопкой.
- Загрузка принимает только дамп формата custom не больше `BACKUP_MAX_UPLOAD_MB`, прошедший `pg_restore --list`, из PostgreSQL не новее серверного.
- Восстановление требует пароль администратора и слово `RESTORE`. Дальше панель включает режим обслуживания (ключ `lecturo:maintenance` в Redis: api отвечает 503 на всё, кроме `/api/v1/health`, `/api/v1/maintenance` и `/api/v1/admin/*`, воркер откладывает новые задачи), ждёт, пока воркер закончит текущие, снимает `pre-restore-<дата>-<время>.dump`, пробно восстанавливает дамп во временную базу `lecturo_check_*`, затем пересоздаёт рабочую базу, применяет недостающие миграции и ставит незаконченные лекции в очередь. Если после пересоздания что-то пошло не так, база возвращается из `pre-restore`.
- Если api перезапустили во время восстановления, сайт остаётся в режиме обслуживания. Проверьте базу и выключите режим кнопкой в панели или командой `docker compose exec redis redis-cli del lecturo:maintenance`.
- Подтвердить восстановление можно только паролем, поэтому администратору, который входит через Telegram, VK или Яндекс, сначала нужно задать пароль в кабинете. Если токен администратора истёк, а режим обслуживания завис, `/api/v1/auth/*` тоже закрыт: снимайте флаг командой `redis-cli del lecturo:maintenance`.
- Скачивание дампа в панели идёт через память браузера, для дампов в несколько гигабайт копируйте файл из `BACKUP_DIR` на сервере.
- Бот подключается к базе напрямую: при восстановлении его соединения обрываются. Если бот не переподключился сам, перезапустите его: `docker compose restart bot`.
